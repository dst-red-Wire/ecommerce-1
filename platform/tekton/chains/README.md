# Tekton Chains preparation

Tekton Chains is pinned in `versions.mk` to `v0.29.0`. The official release
manifest is expected at:

`https://infra.tekton.dev/tekton-releases/chains/previous/v0.29.0/release.yaml`

Its expected SHA-256 is also pinned in `versions.mk`. A future installer must
download that exact URL, verify the checksum, perform a server-side dry-run on
`ecommerce-staging`, and only then apply it remotely.

Chains is intentionally not referenced by the integration Kustomization yet.
The controller needs two capabilities which are not available in Git:

1. `tekton-chains/signing-secrets`, containing an x509/Cosign signing key or a
   configured KMS reference. No key is generated by this repository.
2. A dedicated `chains-ghcr-write` registry credential attached only to
   `tekton-chains-controller`, so completed PipelineRun provenance can be stored
   beside the GHCR image without exposing registry write access to tests,
   scanners, or evidence Tasks.

`chains-config.yaml` disables TaskRun storage/signing and enables SLSA
provenance only at the deeply inspected, completed PipelineRun boundary. This
prevents the raw `build-push` TaskRun from being confused with final approval.
Only Pipeline results use the `IMAGE_URL`/`IMAGE_DIGEST` type hints. No Task
result uses those names. Generic TaskRun OCI result signing is explicitly
disabled because Chains v0.29.0 cannot safely turn a successful early image
push into final approval. The authoritative Chains object is deeply inspected
completed PipelineRun provenance stored through the controller identity.
Provenance and the environment-specific signed `PromotionProof` remain
separate; neither one alone authorizes promotion. Public transparency logging
remains disabled until its privacy and availability implications are approved.

`signing-secret.contract.yaml` and `registry-secret.contract.yaml` are metadata,
not Kubernetes Secrets. Runtime validation must prove the official
`tekton-chains-controller` ServiceAccount, the expected `chains-config`
ConfigMap and both out-of-band contracts. Until that happens, status is
`NOT PROVEN`.

For production, a KMS-backed signer is preferred. The x509 contract is suitable
for integration only when its private key is provisioned and rotated outside
Git. Installation must stop if either signing or GHCR credentials are absent.

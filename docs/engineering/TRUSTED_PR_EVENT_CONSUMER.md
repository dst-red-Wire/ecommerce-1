# Trusted PR event consumer (proposed external transport)

Owning domain: repository delivery governance. This is a forge-event adapter, not a CI authority. Tekton remains the source of exact-SHA qualification evidence. The normative contracts are `architecture.lock.yaml#repository_governance.owner_authorization` and `config/contracts/review-policy.yaml#repository_delivery`.

The external webhook receiver dispatches authenticated `pull_request` (`opened`, `synchronize`, `reopened`, `ready_for_review`) and `issue_comment.created` events to `scripts/trusted_pr_event_consumer.py`. The adapter validates `X-Hub-Signature-256` against `TRUSTED_PR_WEBHOOK_SECRET`, ignores unrelated comments, and reloads the live PR/base/head from GitHub. It never treats event payload SHAs or comment bodies as merge authority.

The receiver must pass the raw body as a private temporary file and the signature header as `--signature`, set `GITHUB_REPOSITORY=dst-red-Wire/ecommerce-1`, provide a repository-scoped GitHub App installation token (preferred) or fine-grained token, and a 32-character-or-longer webhook secret. Serialize invocations per PR. Run the receiver on a hardened external worker with Python 3, Git, GitHub CLI, ORAS and Cosign provisioned from pinned packages. Its `PATH` must contain only trusted system binaries, never the PR checkout. Do not register the webhook until this separate SENSITIVE PR is approved, merged, and its external runtime is provisioned.

Credential phases are deliberately disjoint:

| Phase | Allowlisted credentials/configuration | Executes HEAD code? |
| --- | --- | --- |
| `WEBHOOK_ENV` | `TRUSTED_PR_WEBHOOK_SECRET` solely for HMAC-SHA256; removed before the first subprocess | No |
| `EVIDENCE_ENV` | `CI_EVIDENCE_REPOSITORY`, read-only OCI auth via a private `DOCKER_CONFIG`, and either public `CI_EVIDENCE_COSIGN_PUBLIC_KEY` or certificate identity/issuer | No; only exact-base evidence code and ORAS/Cosign |
| `TRUSTED_GITHUB_ENV` | `GH_TOKEN`/`GITHUB_TOKEN` and `GITHUB_REPOSITORY` | No; only exact-base wrapper/controller and GitHub CLI/merge operations |
| `HEAD_EXEC_ENV` | `PATH`, `LANG`, `LC_ALL`, `TZ`, `PYTHONIOENCODING` | Possible, but no credentials or runner-specific variables |

Do not configure `CI_EVIDENCE_COSIGN_KEY` (a signing key) for verification. The registry credential must be read-only and restricted to the evidence repository. Store webhook, GitHub and OCI credentials separately with private filesystem permissions; do not mount credential files or expose the trusted process namespace to an untrusted checkout. Never log an environment dump, token, Authorization header or credential-bearing CLI error. Bounded retry and a DLQ belong to the external serialized dispatcher, keyed by GitHub delivery ID and current PR SHA.

The GitHub token needs only this repository's [Contents write for exact-SHA merge and branch deletion](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request), [Pull requests read for PR state and comments](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request), [Administration read for branch protection](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection), [Checks read](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference), and [Commit statuses read](https://docs.github.com/en/rest/commits/statuses#get-the-combined-status-for-a-specific-reference). Metadata read is implicit for a GitHub App; applicable branch rules need [Metadata read](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch). No Administration write, broad organization permission or admin bypass is needed. Confirm the precise token type and branch restriction on a staging runner before activation.

For each eligible event the adapter creates temporary, distinct exact-base and exact-head checkouts. Exact-base `repository_delivery.py` verifies a signed Tekton evidence artifact; exact-base `performance_audit.py` runs with `HEAD_EXEC_ENV`. The exact-base wrapper then runs a read-only `--dry-run --json` and must report qualification `PASS` before any mutating transition. Missing or invalid evidence blocks the event; the trusted controller cannot fall back to HEAD qualification while it owns a GitHub token. After the preflight it invokes the exact-base `trusted-pr-transition` once. That controller alone evaluates CODE, SECURITY, risk and owner authorization, and performs any permitted merge and cleanup. `finish-pr` calls its signing rotation gate from the exact-base checkout, not the PR head. Any other child command defaults to `HEAD_EXEC_ENV`; only GitHub CLI, the exact-base controller, and a hook-disabled exact-lease Git push receive the GitHub credential. The exact-base wrapper resolves and pins absolute GitHub CLI and Git paths from the trusted runner `PATH`, rejects tools under the PR HEAD, and passes those paths to the controller. In trusted mode the controller never prepends a managed bin directory from the HEAD `toolchain-lock.json`; `gh` commands use only the pinned CLI, an explicit different `gh` is rejected, and the Git credential helper for push names the pinned CLI by absolute path. If the head or base changes, all exact-SHA evidence becomes historical and the invocation blocks or restarts on the next event. A draft PR remains blocked from mutation.

Subprocess audit for `pr-loop`, `finish-pr` and post-merge cleanup: exact-base wrapper/controller, risk classifier, signing rotation and roadmap checker are `TRUSTED_BASE_CODE`; pinned `gh` is the credentialed `EXTERNAL_TOOL`; `git` fetch/status/switch/merge is credential-free `EXTERNAL_TOOL`; exact-lease push uses pinned Git and a pinned GitHub CLI credential helper with hooks disabled; `performance_audit.py` is exact-base code but runs without credentials; missing-evidence qualification and drift-triggered roadmap delivery are blocked rather than running HEAD code with the merge token. Any future relative `scripts/*` subprocess is treated as `HEAD_CODE` and receives only `HEAD_EXEC_ENV` by default. Tests execute a tampered HEAD script as a real subprocess and assert absence of webhook, GitHub, OCI and arbitrary runner secrets; a separate real subprocess test changes the HEAD toolchain lock to inject a fake `gh` and proves that it is never selected or tokened.

This repository intentionally has no `.github/workflows` delivery workflow: `config/contracts/ci-topology.yaml` forbids GitHub Actions as a parallel CI authority. Webhook registration, runner hardening, secret provision and serial dispatch are external operational prerequisites, not claims made by this PR. The current PR is SENSITIVE and must receive exact-SHA qualification, ChatGPT CODE and SECURITY reviews, and explicit repository-owner authorization before merge.

Rollback: disable the external webhook/worker; revert this PR if the adapter itself needs removal. The merged one-shot bootstrap for PR #162 is not a runtime dependency and must not be reused.

Expected evidence: event-routing/HMAC/credential-isolation unit tests, governance gate, exact-SHA qualification from Tekton, CODE/SECURITY markers and owner authorization for this PR, plus a staging webhook replay before production registration.
